## Блокирующие вопросы первого раунда

### Q1. Продуктовая граница и форма поставки

**Почему важно:** от этого зависят публичный API, упаковка, миграции, необходимость auth, выбор GUI и даже структура БД. Нельзя одновременно делать «личный скрипт» и «сервер на несколько пользователей» без разных архитектурных решений.

**Варианты:**

1. **Личный локальный инструмент + переиспользуемая библиотека.** Один пользователь, Linux, CLI и Python API; GUI позже; без сервера, auth и мультитенантности. Публикация не приоритет, но контракты остаются чистыми.
2. **Open-source приложение для других людей.** Кроссплатформенность, установка «в один клик», миграции, документация, GUI важнее, чем в (1).
3. **Библиотека/бэкенд для другого проекта.** API-first, стабильные контракты, минимум CLI; интеграция важнее пользовательского опыта.
4. **Многопользовательский сервер.** Auth, изоляция, очереди, PostgreSQL, конкурентные пользователи.

**Рекомендация:** вариант 1. Он соответствует исходной идее, не мешает позже вынести API/HTTP и не заставляет платить за серверную сложность сейчас.

**Ответ:** вариант 1 — личный локальный инструмент + переиспользуемая библиотека. Следствия: без auth и мультитенантности, Linux-first, публичный Python API проектируем аккуратно, но без обязательств semver для внутренних модулей.

### Q2. Первый вертикальный срез (MVP)

**Почему важно:** определяет, какие адаптеры и анализаторы пишем первыми, и что считаем «готово». Нельзя начинать с плейлиста и GUI одновременно.

**Варианты:**

1. **Один трек из любого источника: локальный файл или одна ссылка.** Без плейлистов. Полный путь: acquire → observe → interpret → resolve → render → publish. Проверяет и скачивание, и ядро метаданных.
2. **Только локальные файлы.** Быстрее, без сети и cookies; проверяет ядро резолва и записи тегов, но не проверяет acquisition.
3. **Только одна ссылка `yt-dlp`.** Главный пользовательский сценарий; локальные файлы добавляются позже.
4. **Плейлист целиком.** Сложнее: план, выбор, лимиты, resume, контекст коллекции. Хороший стресс-тест, но плохой первый срез.

**Рекомендация:** вариант 1. Он даёт целостный продукт на одном треке и не раздувает скоуп. Плейлист — следующий срез.

**Ответ:** вариант 1 — один трек из любого источника. Плейлисты, пакетная обработка и GUI — следующие срезы.

### Q3. Политика записи и управления библиотекой

**Почему важно:** это вопрос сохранности данных и всей модели хранения. От него зависит, можно ли перегенерировать результат, как работает undo и что попадает в каталог.

**Варианты:**

1. **Управляемая библиотека.** Оригинал не трогаем; копируем/импортируем в библиотеку, пишем теги в копию, рядом кладём sidecar `trackforge.json`. Оригиналы остаются источником правды.
2. **Тегировать на месте, с бэкапом.** Удобно для уже существующей библиотеки, но любой баг writer'а опасен; нужен undo/backup.
3. **Только sidecar, без записи тегов.** Максимально безопасно и просто, но не решает главную задачу — «нормальные теги в файле».
4. **Настраиваемо, по умолчанию managed.** Гибко, но больше кода, тестов и UI-сценариев.

**Рекомендация:** вариант 1 (с возможностью явного in-place режима позже). Это даёт безопасность, воспроизводимость и чистую модель «источник → производные».

**Ответ:** вариант 1 — managed library + sidecar. In-place режим возможен позже как явная опция, но не по умолчанию.

### Q4. Кто принимает финальное решение при конфликтах метаданных

**Почему важно:** это ядро продукта. Если LLM получает право писать финальные значения без ограничений, теряется объяснимость и воспроизводимость. Если решает только приоритет источников, теряется консенсус и контекст.

**Варианты:**

1. **Детерминированный policy engine; LLM — один из источников и арбитр только там, где это разрешено политикой.** Правила, confidence, консенсус, приоритеты, review. LLM возвращает структурированные claims с цитатами.
2. **LLM-арбитр по всем полям.** Потенциально «умнее» на сложных случаях, но дорого, нестабильно, трудно объяснить и воспроизвести.
3. **Всегда человек в цикле.** Надёжно, но медленно; не масштабируется на плейлисты.
4. **Только приоритет источников.** Просто и предсказуемо, но не использует согласие источников, контекст и тип трека.

**Рекомендация:** вариант 1. LLM может быть арбитром, но как явно включённый шаг с ограниченными правами, а не как «мозг» всей системы.

**Ответ:** вариант 1 + пользовательская опция «LLM решает всё» (autopilot) через API. Дополнительно: система обязана сохранять все случаи, когда итог разошёлся с желанием пользователя, в отдельный журнал/датасет для последующей калибровки политик, промптов и анализаторов. Детали — Q19–Q21.

### Q5. Интерфейсы в v1

**Почему важно:** GUI может «протечь» в домен и удвоить стоимость изменений. Нужно заранее решить, что является первичным интерфейсом.

**Варианты:**

1. **CLI + Python API; GUI позже.** Вся логика — в application services; CLI — тонкий адаптер. Будущий GUI подключается через те же сервисы (позже — локальный HTTP API).
2. **Сразу локальный web UI** (FastAPI + frontend). Удобно, но требует фронтенда, SSE/WebSocket, аутентификации локального API и больше тестов.
3. **Сразу нативный desktop** (PySide6). Привычный GUI, но сложная упаковка и кроссплатформенность.
4. **TUI на Textual.** Компромисс для терминала, но не полноценный GUI.

**Рекомендация:** вариант 1. Сначала доказать ядро, потом строить GUI на стабильных сервисах.

**Ответ:** вариант 1 — CLI + Python API; GUI позже.

### Q6. Обязательные анализаторы в v1

**Почему важно:** CPU-only и ограниченное время. Если включить всё сразу, MVP превратится в исследовательский проект. Нужно выбрать минимальный набор, который даёт заметную пользу.

**Варианты (можно выбрать несколько):**

1. **Метаданные источника + существующие теги + `ffprobe`.** База: что уже известно, длительность, формат, битрейт, встроенные теги.
2. **Акустика: BPM, key, loudness, duration.** Относительно дешёво на CPU; полезно для тегов и derivative-детекции.
3. **AcoustID + MusicBrainz + обложки.** Сильная идентификация и внешние метаданные; сеть, rate limit.
4. **LLM-интерпретация описания/названия.** Дешёвый текст, потенциально высокая польза для «настоящего названия» и типа.
5. **ASR/транскрипция + LRC.** Дорого на CPU, но нужно для текста и таймингов.
6. **Demucs/стемы + вокальный анализ.** Очень дорого на CPU; полезно для instrumental/acapella и качества.
7. **Детектор derivative (nightcore/remix/sped up).** Специфичная ценность проекта; можно начать с правил + метаданных, без тяжёлых моделей.

**Рекомендация для v1:** 1 + 2 + 3 + 4 + 7 (в упрощённом виде). ASR и Demucs — следующий срез, после бенчмарков на целевом CPU.

**Ответ:** все перечисленные анализаторы доступны; тяжёлые (ASR, Demucs) можно явно отключать/пропускать. Для каждого результата — цепочки альтернативных провайдеров; если данных нет и альтернативы нет, это фиксируется как деградация, а не молчаливый пропуск.

### Q7. Облачные LLM/API и приватность

**Почему важно:** определяет, какие анализаторы можно делать, как хранить секреты, как считать стоимость и что писать в политике приватности. Отправка аудио в облако — качественно другой риск, чем отправка текста.

**Варианты:**

1. **Текст — можно в облако; аудио — только явный opt-in; локальный fallback 0.5B — опционально.** Провайдер-агностик, бюджет, логирование стоимости.
2. **Только локальные модели.** Приватно, но CPU-only делает ASR/LLM медленными; качество ниже.
3. **Можно всё, включая аудио.** Максимальное качество/скорость, но выше стоимость и риск.
4. **Без LLM в v1.** Проще, но теряется часть ценности на шумных описаниях.

**Рекомендация:** вариант 1. Текст — да (с настраиваемым провайдером), аудио — только по явному согласию, локальный 0.5B — опциональный fallback.

**Ответ:** вариант 1 — текст в облако можно, аудио только opt-in, локальный fallback 0.5B опционален; 7B/13B не планируются.

## Блокирующие вопросы второго раунда

### Q19. Что считать расхождением с желанием пользователя

**Почему важно:** от этого зависит, какие события вообще попадают в датасет. Если писать всё подряд, датасет зашумится; если только явные правки, можно пропустить важные сигналы.

**Варианты:**

1. **Явные правки в TrackForge** (review/override, CLI-команда `feedback`) — пользователь сам меняет решение или помечает «неверно». Для MVP этого достаточно.
2. **Плюс детект ручных правок выходных файлов** при следующем сканировании: сравнили теги/имя/обложку с последним `DecisionRecord` — если отличаются, создали `Correction` с `source=external_edit`.
3. **Плюс неявные сигналы**: пользователь пропустил кандидата, отменил скачивание, удалил результат. Это не `Correction`, а отдельные low-weight события.
4. **Всё сразу с первого дня.**

**Рекомендация:** вариант 1 в MVP, вариант 2 закладываем в модель и добавляем сразу после MVP; вариант 3 — отдельный тип событий, не смешивать с correction.

**Ответ:** вариант 1 — явные правки в TrackForge. Детект внешних правок и неявные сигналы закладываем в модель, но не включаем в MVP.

### Q20. Область применения правки

**Почему важно:** если каждая правка автоматически становится глобальным правилом, один случай может испортить поведение на всей библиотеке. Если правка никогда не обобщается, пользователь будет править одно и то же вручную.

**Варианты:**

1. **Item-level по умолчанию; пользователь может явно повысить правку до правила** (для артиста, источника, профиля). (Recommended)
2. Только item-level, без обобщения.
3. Автоматически обобщать по артисту/источнику, если похожие правки повторяются.
4. Сразу глобальное правило.

**Рекомендация:** вариант 1. Автоматическое обобщение — позже и только с подтверждением.

**Ответ:** вариант 1 — item-level по умолчанию + явное повышение до правила (source/artist/profile/global).

### Q21. Границы режима `llm_autopilot`

**Почему важно:** «LLM решает всё» может означать и «выбирает лучший из готовых claims», и «сочиняет новые факты». Это разные уровни риска и разные требования к валидации.

**Варианты:**

1. **LLM выбирает из существующих claims и может синтезировать производное значение** (например, `Title (Nightcore)`) с явным `derived_from`; не выдумывает новые MBID/ISRC/URL; пользовательские locks всегда сильнее. (Recommended)
2. LLM может свободно придумывать значения, включая новые названия, артистов и ID.
3. LLM только ранжирует существующие claims, без синтеза.
4. Autopilot разрешён только для выбранных полей (например, title/artist/genre), а остальные — policy.

**Рекомендация:** вариант 1 + возможность ограничить autopilot списком полей (совместимо с 4).

**Ответ:** вариант 1 — LLM выбирает из claims и может синтезировать производное значение с `derived_from`; не выдумывает новые MBID/ISRC/URL; locks всегда сильнее. Autopilot можно ограничить списком полей.

### Q22. Поведение при деградации

**Почему важно:** на CPU тяжёлые анализаторы могут быть отключены, сеть — недоступна, провайдер — сломан. Нужно заранее решить, что считается ошибкой, а что — допустимым ухудшением.

**Варианты:**

1. **Обязательные выходы → fail/review; опциональные → `degraded` + видимое предупреждение.** (Recommended)
2. Всегда деградировать, никогда не падать.
3. Всегда падать, если любой включённый анализатор недоступен.
4. Спрашивать пользователя каждый раз.

**Рекомендация:** вариант 1. Обязательный выход — успешно созданный выходной файл; `title`/`artist` — желательные, но не обязательные. Остальное — по политике.

**Ответ:** обязательным является только успешно созданный выходной файл; его отсутствие — ошибка. `title` и `artist` — желательные, но не обязательные: при невозможности можно оставить `unknown`.

При недоступности сети/провайдера допустима деградация на локальную 0.5B или на **не-генеративную модель выбора из конечного набора вариантов** (ranker/reranker). Для отключённых тяжёлых анализаторов — упрощённые версии (например, акустика без Demucs, lyrics без ASR). Любая деградация должна быть видимой и записанной.

### Q23. Лицензия проекта

**Почему важно:** `mutagen` — GPL-2.0-or-later, `essentia` — AGPL-3.0-only. Если бы проект остался MIT и распространялся как единое целое, это могло быть несовместимо. Решение влияет на tag-writer и на возможность использовать TrackForge как библиотеку в другом проекте.

**Варианты:**

1. **MIT core + GPL-адаптеры отдельными пакетами/plugins** (mutagen/Essentia не входят в MIT-ядро). (Recommended)
2. **GPL-3.0-or-later для всего проекта.** Проще с зависимостями, но другое использование TrackForge должно быть GPL-совместимым.
3. **MIT + избегать GPL в core:** tag-writer через `ffmpeg`/TagLib (LGPL), без Essentia. Больше работы, меньше покрытия.
4. Решить позже; пока считать проект «только для личного использования».

**Рекомендация:** вариант 1, если важна возможность переиспользования в проектах с другой лицензией; вариант 2, если проект останется личным/open-source и проще использовать лучшие GPL-инструменты.

**Ответ:** целевая лицензия — **GPL-3.0-or-later**, если это не требует сложной перестройки. Проект пока личный. Желательно не завязываться жёстко на GPL/AGPL: держать такие зависимости за портами и optional adapters, чтобы при желании можно было перелицензировать ядро и заменить адаптеры. Если изоляция окажется слишком дорогой или сузит возможности — принимаем GPL и пользуемся лучшими инструментами.

Практический план: GPL-3.0-or-later для репозитория; `mutagen` — GPL-совместимый адаптер; `essentia` (AGPL) — отдельный optional plugin с предупреждением; домен и application не импортируют GPL/AGPL-библиотеки.

### Q24. Обязательные форматы в MVP

**Почему важно:** от этого зависит объём tag-writer'а, тестовые фикстуры и то, какие поля вообще можно записать.

**Варианты:**

1. **MP3 + M4A/AAC + FLAC + OGG/Opus.** (Recommended)
2. MP3 + M4A/AAC.
3. Плюс WAV/AIFF/ALAC/WMA.
4. Все форматы, которые поддерживает выбранная библиотека.

**Рекомендация:** вариант 1. Этого достаточно для музыки и большинства источников; WAV/AIFF — позже, если понадобятся.

**Ответ:** вариант 1 — MP3, M4A/AAC, FLAC, OGG/Opus.

## Блокирующие вопросы третьего раунда

### Q25. Подтверждение смены `LICENSE`

**Почему важно:** в репозитории был MIT, а целевая лицензия — GPL-3.0-or-later. Пока файл не изменён, документы и реальность расходятся. При этом проект пока личный, и смена лицензии обратима для собственного кода (но не для уже распространённых версий).

**Варианты:**

1. **Сменить `LICENSE` на GPL-3.0-or-later сейчас.** (Recommended)
2. Оставить MIT до публикации; в документах зафиксировать целевую GPL.
3. Сделать MIT-ядро + отдельные GPL-пакеты/adapters (multi-license).
4. Отложить.

**Рекомендация:** вариант 1, раз проект личный и целевая лицензия уже выбрана; architecture boundary всё равно сохраняет возможность заменить GPL-адаптеры.

**Ответ:** вариант 1 — `LICENSE` заменён на GPL-3.0-or-later. License boundary сохранён: ядро не импортирует GPL/AGPL, адаптеры остаются заменяемыми.

### Q26. Fallback-ranker по умолчанию

**Почему важно:** это решает, насколько качественно система работает без облачной LLM и сколько зависимостей тянет. Ranker не генерирует текст, поэтому дешевле и стабильнее, но требует модели.

**Варианты:**

1. **Гибрид: лексический baseline + cross-encoder (CPU/ONNX); 0.5B fallback — опционально.** (Recommended)
2. Только лексический baseline (`rapidfuzz`/нормализация) — минимум зависимостей.
3. Только cross-encoder.
4. Только локальная 0.5B.

**Рекомендация:** вариант 1. Лексика работает всегда и мгновенно; cross-encoder даёт качество на нечётких вариантах; 0.5B — только если реально помогает.

**Ответ:** вариант 1 — гибрид: lexical baseline + cross-encoder (CPU/ONNX); 0.5B fallback опционален, 7B/13B не планируются.

### Q27. Политика источников

**Почему важно:** кастомные парсеры дают больше покрытия, но увеличивают поверхность поддержки, юридические риски и сложность plugin-модели.

**Варианты:**

1. **`yt-dlp` + официальные/публичные API; кастомные источники — только как plugins.** (Recommended)
2. Встроенные кастомные парсеры для конкретных сайтов.
3. Только `yt-dlp`.
4. Универсальный HTML-парсер для любого сайта.

**Рекомендация:** вариант 1. Это соответствует исходной идее и не превращает ядро в зоопарк парсеров.

**Ответ:** вариант 1 — `yt-dlp` + официальные/публичные API; кастомные источники только как plugins.

### Q28. Шаблон имени файла по умолчанию

**Почему важно:** имя файла — часть пользовательского результата; оно должно быть предсказуемым, безопасным для ФС и учитывать derivative-версии.

**Варианты:**

1. **`{title} - {artist} ({qualifier})`**, где `qualifier` — nightcore/remix/...; для неизвестных — резервный шаблон. (Recommended — соответствует примеру из исходной идеи)
2. `{artist} - {title} ({qualifier})`.
3. `{artist} - {album} - {track:02d} - {title}`.
4. Без дефолта, только конфиг.

**Рекомендация:** вариант 1 как дефолт + настраиваемый шаблон. Для `unknown` — `Unknown Title - Unknown Artist [<short-id>]`.

**Ответ:** вариант 2 — `{artist} - {title} ({qualifier})`. Для `unknown` — резервный шаблон с коротким id.

### Q29. Дефолтный профиль анализа

**Почему важно:** CPU-only. Если по умолчанию включить Whisper и Demucs, первый запуск может занять десятки минут; если выключить слишком много — пострадает качество.

**Варианты:**

1. **`balanced` по умолчанию; `full` (ASR/Demucs) — явно.** (Recommended)
2. `full` по умолчанию с предупреждением.
3. `fast` по умолчанию.
4. Спрашивать при первом запуске.

**Рекомендация:** вариант 1. Дешёвые шаги + LLM + derivative-детектор дают основную пользу; тяжёлое — осознанный выбор.

**Ответ:** вариант 1 — `balanced` по умолчанию, `full` opt-in.

### Q30. Обложка и lyrics по умолчанию

**Почему важно:** форматы по-разному поддерживают встраивание lyrics; LRC в теге поддерживается не везде. Нужно выбрать предсказуемое поведение.

**Варианты:**

1. **Обложка встраивается; plain lyrics — в тег, если формат поддерживает; LRC — sidecar.** (Recommended)
2. Встраивать и обложку, и lyrics (включая LRC, где поддерживается).
3. Только sidecar (cover.jpg + lyrics.lrc).
4. Настраиваемо профилем.

**Рекомендация:** вариант 1. Максимальная совместимость и предсказуемость; LRC всегда доступен рядом.

**Ответ:** вариант 1 — cover embed + plain lyrics в тег (если поддерживается) + LRC/ELRC **только sidecar**. Встраивание LRC пока не делаем.

4. Только конфиг.

### Q32. Платформы и масштаб

**Почему важно:**

- ОС влияет на пути, file lock, reserved names, упаковку `ffmpeg`/`fpcalc`, GUI.
- Размер библиотеки влияет на индексы SQLite, скорость scan, duplicate detection, память и будущий UI.
- Размер плейлиста влияет на очередь, resume, rate limits и стратегию «не качать всё сразу».

**Подвопросы:**

1. **ОС в v1:** только Linux / Linux + Windows / Linux + Windows + macOS.
2. **Размер личной библиотеки:** до 1k / 1k–10k / 10k–100k / >100k треков.
3. **Максимальный плейлист:** до 50 / до 500 / до 5000 / без практического лимита.

**Рекомендация:** Linux-only v1; целевой размер 1k–10k; плейлисты до 500 с паузами/resume. Для 10k+ SQLite/индексы уже проектируем, но тяжёлый scan/duplicates — позже.

**Ответ:** Linux-only в v1; целевая библиотека 1k–10k треков; плейлисты до 500 с паузами/resume. Windows/macOS и 10k+ — позже, но индексы/пути проектируем с запасом.

### Q17. Управление моделями и offline
