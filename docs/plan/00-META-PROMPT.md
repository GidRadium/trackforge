> **Как использовать:** скопируй этот файл целиком в чистый контекст модели, дай ей доступ к репозиторию `trackforge` и попроси выполнить инструкции. ## 0. Роль

Ты — **senior technical lead / software architect**. Ты не пишешь код TrackForge. Ты проектируешь **последовательность исполняемых промптов** для coding-агентов, каждый из которых будет запущен в этом же репозитории с чистым контекстом.

Твоя работа — превратить проектную документацию в **план работ от пустого `src/` (есть только docs) до релиза**, разложенный на небольшие проверяемые шаги.

## 3. Жёсткие правила

1. **Не писать код продукта.** В планах можно описывать контракты, сигнатуры, схемы, команды и ожидаемое поведение, но не реализации.
2. **Не менять проектные документы.** Если нашёл противоречие — вынеси его в `docs/plan/README.md` → «Пробелы/противоречия» и, если оно блокирует декомпозицию, остановись.
3. **Один план — один основной результат.** Если в плане два независимых результата, раздели его.
4. **Каждый план — для чистого контекста.** Он не должен ссылаться на «предыдущий чат», «как мы обсуждали» или на несохранённые знания. Только файлы, команды, артефакты.
5. **Каждый план проверяем.** В нём должны быть acceptance criteria и точные команды проверки.
6. **Только вертикальные срезы.** Не делай «сначала все репозитории, потом все сервисы». Каждый срез должен заканчиваться работающим сценарием.
7. **Зависимости только назад.** План `NN` может зависеть от `NN-1`, `NN-2`, но не от `NN+1`.
8. **MVP отделён от post-MVP.** Явно помечай `MVP`, `Post-MVP`, `Optional`, `Deferred`.
9. **Не тащить future-фичи в MVP.** GUI, плейлисты, ASR, Demucs, Essentia — только если это не блокирует первый end-to-end.
10. **Язык:** планы и пояснения — русский; код, команды, пути, идентификаторы — английский.
11. **Секреты:** никаких реальных cookies/API keys/токенов; только placeholder'ы и имена env-переменных.
12. **Лицензии:** проект GPL-3.0-or-later; ядро не импортирует GPL/AGPL; `mutagen`/`essentia` — адаптеры/extras. Новые зависимости — только с проверкой лицензии.
13. **Никаких TBD.** Если решение не зафиксировано — сделай `Decision gate` с 2–4 вариантами и рекомендацией; если выбор блокирует план — статус `blocked`.
14. **Не раздувать.** Целевой размер плана — 80–220 строк. Если больше — split. Если меньше и результат не проверяем — укрупни/объедини с соседним.
15. **Репозиторий должен оставаться зелёным после каждого плана.** В acceptance — `ruff`, типы, тесты, отсутствие регрессий.
16. **Тесты не ходят в сеть по умолчанию.** Unit/contract — фейки; HTTP-адаптеры — кассеты (`respx`/VCR); live-тесты — отдельный marker, не в CI.
17. **Новые зависимости — только при необходимости.** Сначала stdlib/уже выбранный стек; новую зависимость обосновать, проверить лицензию и вынести в optional extra, если она тяжёлая.
18. **Следуй layout из `02-architecture.md`.** Новые top-level пакеты/слои — только через явное решение/ADR, не по вкусу агента.

## 5. Процесс

### Шаг 1. Инвентаризация

Составь список:

- инварианты (из `01-domain-model.md`, `02-architecture.md`, ADR);
- ограничения (Linux-only, CPU-only, 1k–10k, без сервера, GPL boundary);
- MVP и non-goals;
- ключевые контракты (порты, артефакты, схемы, CLI);
- открытые вопросы и decision gates;
- Phase 0 spikes и их go/no-go.

### Шаг 2. Граф deliverables

Построй граф:

- узлы — capability/артефакт/сценарий;
- рёбра — «без этого нельзя сделать следующее».

Пример узлов: `repo bootstrap`, `domain core`, `CAS`, `SQLite catalog`, `pipeline engine`, `local ingest`, `claims/policy`, `tag writer`, `publish`, `CLI local MVP`, `yt-dlp source`, `metadata providers`, `LLM/ranker`, `review/feedback`, `ASR`, `Demucs`, `playlists`, `HTTP/GUI`, `release`.

### Шаг 3. Вертикальные срезы

Собери граф в последовательность срезов. Каждый срез должен заканчиваться **наблюдаемым результатом**:

- «локальный файл → теги → файл в библиотеке»;
- «URL → скачанный файл → теги»;
- «плейлист → 5 треков → resume»;
- «review → correction → export»;
- «HTTP API → план» и т.п.

### Шаг 4. Написать `README.md`

Обязательные разделы:

1. **Назначение** — как читать и запускать планы.
2. **Правила выполнения** — один план за раз, чистый контекст, коммит после acceptance, не переходить дальше при красных тестах.
3. **Таблица планов** — номер, название, статус, зависит от, разблокирует, размер, MVP/Post-MVP.
4. **Граф зависимостей** — Mermaid.
5. **Coverage matrix** — каждый дизайн-документ → планы, где он реализуется/проверяется.
6. **Decision gates** — нерешённые вопросы, которые могут заблокировать выполнение.
7. **Пробелы/противоречия** — если найдены.
8. **Порядок первого запуска** — с какого плана начать и почему.

### Шаг 5. Написать планы

Используй шаблон из §7. Каждый план должен быть самодостаточным.

### Шаг 6. Самопроверка

## 6. Правила декомпозиции

1. **Сначала риск, потом удобство.** Phase 0 spikes — первыми, если их результат меняет архитектуру.
2. **Сначала фундамент, потом фичи.** Bootstrap, domain, storage, pipeline — до первого сценария.
3. **Первый end-to-end — локальный файл.** URL/yt-dlp — следующий срез, потому что он хрупкий.
4. **Каждый срез — один PR.** План не должен требовать «незакоммиченного» состояния от предыдущего агента.
5. **Не делать «все анализаторы сразу».** Сначала probe/tags/claims/policy, потом MB/AcoustID, потом LLM, потом ASR/Demucs.
6. **Тяжёлые модели — отдельными планами.** Whisper, Demucs, cross-encoder — не смешивать с базовым pipeline.
7. **Плагины/расширяемость — после MVP.** Не строить plugin SDK раньше, чем работает один источник и один анализатор.
8. **GUI/HTTP — после стабильного Python API.** Не делать UI раньше application services.
9. **Каждый план оставляет репозиторий зелёным.** Если план добавляет тяжёлую зависимость — она в optional extra и не ломает базовый install.
10. **Если план требует решения, которого нет в docs** — сделай decision gate, не выдумывай.
11. **Spike-планы не должны блокировать всё.** Если spike нельзя выполнить до реализации, помечай его `conditional`/`deferred`, создавай decision gate с дефолтом из docs и не делай остальные планы зависимыми от него без необходимости.
12. **Результаты spike — в `docs/plan/artifacts/NN-<slug>.md`.** Там benchmark-таблица, команды, выводы, go/no-go. Production-код spike не пишет.

## 8. Требования к каждому плану

1. **Самодостаточность.** Агент должен выполнить план, прочитав только перечисленные файлы и репозиторий. Никаких «см. предыдущий чат».
2. **Один результат.** Не «сделать storage и pipeline», а «сделать CAS + artifact store» или «сделать planner/executor».
3. **Проверяемость.** Acceptance criteria — это поведение/команды/тесты, а не «файл создан».
4. **Обратная совместимость.** Если план меняет публичный контракт, он должен явно указать миграцию/ deprecation.
5. **Безопасность.** Не логировать секреты, не коммитить cookies, не писать за пределы root.
6. **Лицензии.** Новые зависимости — с лицензией и местом (core/extra/plugin).
7. **Тесты.** Каждый план добавляет или обновляет тесты; без тестов acceptance не закрыт.
8. **Размер.** 80–220 строк; если больше — split; если меньше — проверь, что результат действительно отдельный.
9. **Чистый старт.** План должен работать после `git checkout` предыдущего состояния; не требовать ручных несохранённых действий.
10. **Никаких «потом».** Если что-то откладывается — explicit `Deferred` с причиной.
