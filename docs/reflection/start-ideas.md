Проект для скачивания, анализа и правильного таггирования и заполнения метаданных аудио файлов (в основном музыки).

Основные источники:
- локальные аудио файлы, папки с аудио файлами
- ссылки на различные медио на сайтах, поддерживаемых yt-dlp + ссылки на плейлисты
- ссылки на сайты, для которых надо отдельно писать парсер/добывать api + тоже плейлисты оттуда, если бывают
- примерное название, автор, публикатор, текстовое описание и прочее, что может быть понятно и найдено LLM, к примеру с помощью web search / web fetch или иных инструментов

Из этих источников получается выбор:
- для локальных - найденный файл/файлы
- для уже известной точной ссылки - варианты качества, расширения, языка (если есть)
- для плейлистов - список имеющихся там треков, их варианты качества, расширения, языка (возможность указать предпочтительные)
- для текстового ввода - список предположительных вариантов (названия, авторы, источник и прочее)

После подстверждения (или без него при желании):
- Скачанный/скопированный файл, а также его метаданные (всё, что можно вытащить с сайта, откуда он получен, к примеру информация из json yt-dlp)
- Для плейлистов желательно реализовать гибкий пайплайн - не всегда хорошая идея всё одновременно качать. (вдруг сайт решит забанить)

Анализ множеством разных способов с целью получаения метаданных, картинок и прочего:
- Экспорт метаданных из json yt-dlp
- Поиск изображения
- Акустический анализ аудио
- Вокальный анализ аудио
- Генерация слов по аудио
- Анализ типа (музыка, аудиокнига, подкаст, прочее)
- Анализ оригинальности (remix, nightcore, прочее)
- Поиск информации о треке, настоящего названия.
- Анализ достоверности различных ранее полученных данных (особенно, если одни и те же отличаются в различных анализаторах)
- Генерация тегов
- Выбор итоговых названия, автора, картинки, тэгов и других метаданных (а также альтернатив). Скорее этот этап - выбор приоритетов в уже существующих вариантах.


Более технические тонкости.
- Проект на Python + uv + pyproject.toml
- Все секреты - в .env
- Надо придумать куда можно кинуть куки (а они разные для разных сайтов).
- Не секретные настройки - в config.txt
- Код в src/trackforge
- cpu only (gpu нет)
- Должны быть cli и gui - как варианты управления проектом (gui - на будущее, пока без него, но декомпозировать с учётом её поддержки)
- Также все функции должны быть корректно выставлены наружу, чтобы для пользователя-программиста (и для cli с gui) было удобно использовать вызывая их из кода. Возможно в дальнейшем буду использовать этот проект как библиотеку в другом своём проекте
- Код должен быть спроектирован таким образом, чтобы было достаточно просто добавить новый источник-сайт (а для тех, которые поддерживаются yt-dlp должно быть ещё проще).
- Добавление нового алгоритма для анализа тоже не должно оказаться серьёзной проблемой.
- Если пайплайн в какой-то момент прерывается, т.е. аудио уже скачано, но ещё не всеми анализаторами проанализированно, то программа не должна с нуля качать файл и проводить уже проведённые анализы (если не желается обратное)
- Основная идея в том, чтобы для каждого анализа генерировался файл с его результатом.
- Я бы вообще анализ разделил на 2 части:
  1) Генерация данных. К примеру получения сырых данных акустики, вокала, транскрипции и других численных и текстовых параметров, путём прохода по всему файлу. Поиск возможных названий по описанию из yt-dlp .json. Запросы к платформам по типу MusicBrainz и подобным. Попытка получить thumbnail, если ещё не получен.
  2) Анализ (интерпритация) сгенерированных данных. По вокалу + акустике понимать, nightcore ли потенциально перед нами. Анализировать описание с помощью LLM на наличие подсказок, original/nightcore/remix/mix/подкаст/аудиокнига/прочее ли это. Выставлять теги и прочее.
  3) Могут ли быть 2 в одном?
- Проще будет, если для каждого генератора/анализатора явно задать, какие данные он требует и какие отдаёт. Так будет куда проще написать пайплайн.
- Генераторы/анализаторы в середине процесса могут возвращать всё, что хотят.
- Идея в том, что всё в конце сводится к генераторам/анализаторам которые возвращают универсальный тип данных, состоящий из:
  1) Предлагаемого названия файла. (Или это можно оставить на потом, но я хочу единый формат, к примеру Title - Author (Nightcore/Remix).m4a/.mp3/...)
  2) Предлагаемых текстовых метаданных. (всех, которые я хочу уметь записывать, включая тэги, для которых есть много строгих и не очень хотелок)
  3) Предлагаемого thumbnail.
  4) Предлагаемых транскрипций (в разных форматах: совсем без меток (записать в метаданные), с метками по строкам, с ещё более частыми метками)
- По списку из которых, по каждому из минипунктов (добавить тэг или нет, выбрать то или иное название) в конце принять решение. Ожидаетя, что у каждого анализатора на выходе большинство полей - None, их пропускаю и смотрю у тех результатов, которые не пустые. Это тоже довлно сложная задача и над её правльной реализацией, что именно выбрать, стоит думать. Например для разных источников данных давать разные приоритеты, и по ним уже выбирать. Или закинуть всё в LLM с правльно написанным промптом.
- Ещё хочется, к примеру, если трек - nightcore, то его корявая транскрипция может быть хуже по качеству слов, чем предоставленная автором (или другими сервисами), но вот метки очень полезны. В теории можно выдать правильную по тексту и правильную по меткам LLM, чтобы она правильно слила их вместе - расставила сгенерированные метки по заведомо правильным словам.
- Если это плейлист с какой-нибудь платформы, я бы хотел, чтобы он выставлял теги в соответствии с этим плейлистом. А ещё лучше спрашивал у пользователя, как он хочет - по плейлисту или по альбому автора.


Как я сейчас вижу самый простой пример работы (все названия и действия приблезительны, не обязательно считать их за истину):

- Пользователь отправляет ссылку на nightcore музыку на ютубе.
- trackforge видит, что дана ссылка => хотим найти способ скачать.
- trackforge перебирает способы скачивания (вызывает .supports(link)) у них. Находит YoutubeDownloader, наследованный от UniversalYtDlpDownloader.
- trackforge спрашивает у него, ссылка на плейлист или на отдельный трек. Получает, что на отдельный трек.
- trackforge стучится к YoutubeDownloader, чтобы он получил доступные варианты через yt-dlp. Отправляет их пользователю, выделяя рекомендованный (самый качественный) вариант для быстрого продолжения.
- Пользователь подстверждает.
- trackforge скачивает трек во временную папку с временным названием.
- trackforge вытаскивает из временного файла метаданные, если они там есть. Стирает их из самого файла.
- trackforge пока хранит у себя .json с данными файла.
- trackforge считает SHA-256 файла и создает папку (в специальной директории, в которой он складывает промежуточные результаты) с названием в виде его SHA-256.
- trackforge кидает туда трек с каким нибудь константным названием. Например track.mp4/.mp3/...
- trackforge создаёт в этой папке файл со стёртыми ранее метаданными (если они сообще были)
- trackforge создаёт файл с .json yt-dlp
- trackforge начинает выполнять разничные генерации/анализы в правильном порядке. (В теории можно для плейлистов или поставить на поток, или делать одновременно несколько, если они независимы и требуют разных ресурсов (cpu/web), но это тоже преждевременная оптимизация. Пока без этого.)
- trackforge Получает список из результатов. Какждый результат - один и тот же тип данных, но просто большинство полей - пустые.
- trackforge определяет какие данные "правильные" и оставляет только их.
- trackforge копирует трек с нужными метаданными, названием и thumbnail в папку с готовыми результатами. (а если это часть плейлиста/альбома то в подпапку этой папки, у которой название как у плейлиста/альбома)
